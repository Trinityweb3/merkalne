## 1. Getting the code onto your machine

Three supported paths, fastest first:

**Option A — download the archive (recommended).**
`merklane-project.tar.gz` is published to the workspace's shared `download/` folder
(the file panel attached to this chat). The archive contains exactly **one
top-level `merklane/` directory**, so it extracts flat into a parent of your
choice. If your working directory is the nested `~/merklane/merklane`:

```bash
tar -xzf merklane-project.tar.gz -C ~/merklane/   # files land in ~/merklane/merklane
cd ~/merklane/merklane
sha256sum -c manifest.sha256 --quiet && echo "tree verified"   # every file byte-identical
```

Never extract *into* the working directory itself (`-C ~/merklane/merklane`) —
that creates `~/merklane/merklane/merklane` (triple nesting), and extracting
over an existing tree leaves stale mixed files behind. If the directory
already exists, move it aside first (see the "Clean redeploy" section in
README.md — `manifest.sha256` tells you in seconds whether a tree is clean).
Note: since the i18n bundle, the Docker build also runs a stale-merge guard
(`docker/check-app-tree.sh`) as its first builder step — merging this bundle
over a pre-i18n checkout aborts the build immediately with the fix steps
instead of failing later with Next.js' cryptic "Ambiguous app routes
detected" error.

**Option B — the self-extracting script.**
`setup-project.sh` (same download folder) contains the entire project as an embedded,
checksum-verified payload. One file, no tar needed:

```bash
bash setup-project.sh            # extracts to ./merklane
bash setup-project.sh ~/code/    # extracts to ~/code/merklane
```

**Option C — copy-paste for individual files.**
Every source file is plain text; the archive also contains a `MANIFEST` file listing
all paths, so you can recreate any single file by hand if you only need a piece.

> There is no "Push to GitHub" from the sandbox. After extracting locally, the
> project is a normal git-ready directory — see §3 for the fresh `git init` steps.

Verify integrity (optional but nice):

```bash
sha256sum -c merklane-project.tar.gz.sha256   # checksum shipped next to the archive
```

## 2. What is inside the archive (and what is deliberately NOT)

**Included:** all source (`src/`, `worker/`, `prisma/`, `scripts/`, `docker/`,
`public/`), every config file (`package.json`, `bun.lock`, `tsconfig.json`,
`next.config.ts`, `tailwind.config.ts`, `postcss.config.mjs`, `eslint.config.mjs`,
`components.json`), `.env.example`, `.gitignore`, `.dockerignore`, `Dockerfile`,
`docker-compose.yml`, `README.md`, this guide, and a `MANIFEST` file list.

**Deliberately excluded (never shipped):**

| Excluded | Why |
| --- | --- |
| `.env` | contained live sandbox values — you generate your own from `.env.example` |
| `node_modules/` | ~500 MB of platform-specific binaries; reinstall locally |
| `.next/`, `dist/` | build output, regenerated on every build |
| `db/` (`custom.db`) | the sandbox's seeded SQLite preview database — your data starts clean |
| `.git/` | sandbox history is not yours; start a fresh repo |
| `dev.log`, `server.log` | sandbox runtime logs |
| `examples/`, `tests/`, `mini-services/`, `tool-results/`, `upload/`, `skills/`, `.zscripts/`, `Caddyfile` | sandbox template/preview tooling, not part of the product |

Because these were excluded at packaging time, **the archive itself needs no cleanup**.
The checklist below exists for completeness — use it if you exported by other means
(e.g. zipped the whole workspace yourself) or want to understand each artifact.

## 3. Post-export cleanup checklist

Only relevant if your copy came from somewhere other than the official archive.
Run from the project root after extraction.

```bash
# --- Dependency & build artifacts (regenerated by install/build) -------------
rm -rf node_modules          # platform-specific binaries — reinstall with bun/npm
rm -rf .next                 # Next.js build cache + output
rm -rf dist                  # bundled worker output (built inside Docker)
rm -rf build                 # generic build dir, if present
rm -rf .turbo                # Turborepo cache, if you ever ran turbo
rm -rf .eslintcache          # lint cache

# --- Secrets — NEVER keep sandbox or foreign .env files ----------------------
rm -f  .env .env.local .env.production .env.development
#    → then: cp .env.example .env  and fill in YOUR values (see §5)
#      (.env* is also in .gitignore, so it will never be committed)

# --- Local databases & logs --------------------------------------------------
rm -rf db                    # SQLite preview DB + journals (created by bun run db:push)
rm -f  dev.log server.log *.log

# --- Editor / IDE noise -------------------------------------------------------
rm -rf .vscode .idea         # sandbox or foreign IDE settings

# --- Git — start fresh if the sandbox .git slipped in ------------------------
rm -rf .git
git init && git add . && git commit -m "Merklane — initial import"

# --- Docker leftovers (if you ran compose on this copy before) ---------------
docker compose down -v       # removes the merklane-pgdata volume + containers
rm -rf postgres-data         # only if you used a bind mount instead of a volume

# --- Sandbox-only directories (only present in workspace dumps) --------------
rm -rf examples tests mini-services tool-results upload skills .zscripts
rm -f  Caddyfile             # sandbox preview reverse-proxy config
```

**Lockfiles — keep one, not several:**

| File | Verdict |
| --- | --- |
| `bun.lock` | **Keep** if you install with Bun (recommended: `bun install`, also used by the Dockerfile) |
| `package-lock.json` | Delete if present and you use Bun; keep instead of `bun.lock` only if you standardise on npm (`npm install` regenerates it) |
| `pnpm-lock.yaml` | Same rule for pnpm — never keep two lockfiles at once |

The archive ships exactly one lockfile (`bun.lock`) that matches `package.json`.

## 4. First local run

**With Docker (closest to production):**

```bash
cp .env.example .env
# minimum: POSTGRES_PASSWORD + AUTH_SECRET (generation commands in §5)
docker compose up -d --build
docker compose logs -f app worker      # migrations run automatically on boot
# → http://localhost:3000  (healthcheck: /api/health)
```

**Without Docker (local PostgreSQL or SQLite preview):**

```bash
bun install                        # or: npm install
cp .env.example .env               # set DATABASE_URL (+ AUTH_SECRET for webhooks)

bunx prisma generate               # Prisma client
bunx prisma migrate deploy         # apply committed migrations (PostgreSQL)
bun prisma/seed.ts                 # optional: reference dataset + demo accounts

bun run dev                        # http://localhost:3000
bun run worker                     # optional: bots worker in a second terminal
```

SQLite preview (no database server at all): set
`DATABASE_URL="file:./db/custom.db"`, `DATABASE_PROVIDER="sqlite"`, then
`bun run db:push && bun run db:preview:generate && bun prisma/seed.ts`.

Without `RESEND_API_KEY` and bot tokens, every flow still runs — emails and bot
messages print to the console instead of being sent.

unconfigured optional features (OAuth buttons, bots) instead of failing silently.

> **Port note (`DB_HOST_PORT`)** — the compose file publishes the bundled PostgreSQL on `127.0.0.1:5433` by default (`127.0.0.1:${DB_HOST_PORT:-5433}:5432`). The 5433 default exists because a native PostgreSQL on the host typically already owns 5432 — starting the stack then aborts with `failed to bind host port … address already in use`. The container-internal port is always 5432 and the app connects as `db:5432` over the internal network, so this mapping only affects host-side access (`psql -h 127.0.0.1 -p 5433 -U merklane`). Override in `.env` (`DB_HOST_PORT=5432`) if your host port is free, or delete the `ports:` block for hardened deployments.

> **Container egress note (Resend / OAuth)** — the app and worker services pin
> `dns: [1.1.1.1, 8.8.8.8]` so external names never depend on the host's
> resolver setup (a loopback `systemd-resolved` stub is unreachable from a
> container). If `api.resend.com`, `oauth2.googleapis.com` or `github.com`
still fail with `ConnectionRefused` from the containers while working from
> the host, the Docker bridge's iptables rules are being dropped by a
> firewall — run `sudo bash docker/fix-container-network.sh` (add `--fix` to
> apply the safe repairs: ip_forward, ufw forward policy, missing
> MASQUERADE/FORWARD rules), then `sudo systemctl restart docker` and
> recreate the stack. If the bridge still refuses, use the shipped escape
> hatch: `docker compose -f docker-compose.yml -f docker-compose.egress.yml
> up -d` (app + worker use the host network — the same path your builds
> already take). Full walkthrough in README.md → *Runtime containers cannot
> reach the internet*.

### Machine translation (Groq/LLM provider chain + LibreTranslate fallback + Web3 glossary)

Job content is translated by the **first configured provider** in this
chain: **Groq → DeepSeek → Google Gemini → self-hosted LibreTranslate**.
On any provider failure (rate limit, timeout, bad response) the same request
falls through to LibreTranslate automatically, and every result is cached
per language in the database. The active provider is shown on `/about`
("Translation via Groq · openai/gpt-oss-120b …").

> **Hashtags are never translated.** `#crypto`, `#defi`, `#rust` … are
> functional identifiers — they power tag filters and `/search?q=%23tag`
> lookups — so they stay byte-identical English in every locale: post tags
> are never sent to the translator, and inline hashtags inside titles and
> bodies are protected as placeholders during the round trip. Section names
> (Intern/Junior, Mid/Senior, Opportunities, Markets, Insights, Blog) stay
> English in every locale for the same reason (routing/DB consistency);
> everything else on the cards and pages is translated.

| # | Variable | Write this (example) | Where to get it | Required? |
|---|----------|----------------------|-----------------|-----------|
| 34a | `GROQ_API_KEY` | `gsk_…` | **Recommended — free tier** (30 req/min, 1 000 req/day, no credit card): console.groq.com → API Keys → “Create API Key” | No |
| 34b | `DEEPSEEK_API_KEY` | `sk-…` | platform.deepseek.com → API keys (paid, no free tier) | No |
| 34c | `GOOGLE_AI_API_KEY` | `AIza…` | aistudio.google.com → “Get API key” | No |
| 35 | `LIBRETRANSLATE_URL` | *(leave empty)* | The always-on **final fallback** — docker-compose wires `http://libretranslate:5000` internally. Set `http://127.0.0.1:5000` only for non-Docker local runs | No |
| 36 | `LIBRETRANSLATE_API_KEY` | *(leave empty)* | Only when you start LibreTranslate with `LT_REQ_API_KEY` | No |

| 38 | `TRANSLATION_GLOSSARY_PATH` | *(leave empty)* | Points at the Web3 glossary JSON; the default `config/translation-glossary.json` is already volume-mounted by compose | No |

> **Groq free-tier notes.** The app uses `openai/gpt-oss-120b` (falls back to
> `qwen/qwen3.8-27b` if that model is ever retired), serializes provider
> requests with ≈2 s spacing to stay under 30 req/min, de-duplicates
> identical strings in a batch, and honors a 429 `Retry-After` header by
> routing requests to LibreTranslate until the window passes. Translation
> results are cached forever per post+language, so the daily quota is only
> spent on **new** content — 1 000 requests/day comfortably covers a fresh
> editorial pass across all 19 non-English locales.

> **Web3 glossary — how jargon survives translation.** A raw translator
> would translate "On-chain" literally and sound robotic. The app swaps every
> glossary term for an opaque placeholder before the request leaves the
> process, and stitches your preferred term back in afterwards:
>
> - A **built-in** glossary is always active: On-chain, Off-chain, DeFi, TVL,
>   AMM, DEX, CEX, DAO, NFT(s), EVM, zkEVM, Layer 1/2, Web3, Yield farming,
>   Stablecoin(s), Airdrop(s), Gas fees, Restaking, …
> - **Your file wins per term**: edit `config/translation-glossary.json`
>   (template with comments: `config/translation-glossary.example.json`).
>   Plain string = same in every language (`"On-chain": "On-chain"` just
>   protects it); per-language object with `"*"` fallback = real replacement
>   (`"Yield farming": { "ru": "Фарминг доходности", "*": "Yield farming" }`);
>   `""` for one language = translate it naturally there.

### Merklane Ads & the site CMS (Telegram)

Two operator features ship in this build:

**Ads (wallet-first).** The advertiser dashboard lives in the profile cabinet at `/profile/ads` (`/ads` redirects there; sign in required). Flow: deposit crypto in the **Wallet tab** → the confirmed deposit lands in the advertiser's wallet (`User.adBalance`) → create a campaign **funded from the wallet** (starts ACTIVE immediately; the budget must cover at least 50 views at the chosen bid, and the wallet must actually hold it — a conditional-decrement transaction guarantees no overdraft). Every served impression deducts the bid from the campaign balance (weighted-random auction: a 2¢ bid wins twice the share of a 1¢ bid) and a drained campaign auto-pauses. Campaigns can also target sections and interface languages (empty = everywhere).

With `BLOCKBEE_API_KEY` set (the production path) the deposit modal shows a **coin picker** (stablecoins + majors on Solana, Polygon, BSC and Arbitrum — TRON is banned by policy), then a **BlockBee-hosted deposit address**. The IPN webhook at `/api/webhooks/blockbee` verifies the signature (RSA `x-ca-signature` and/or the HMAC `token`), matches `order_id` + per-intention nonce against the pending intention, and credits the wallet exactly once — the dashboard's status polling flips to "confirmed" automatically. Without a processor key the flow falls back to `manual` mode: a locally derived mock address is shown and an ADMIN confirms deposits after checking the wallet (`POST /api/admin/ads/topups/<id>/confirm`). For local demos set `ADS_TOPUP_MODE=simulate` and the advertiser sees a "Simulate payment" button instead.

**Referrals.** Every account gets a shareable code — the profile's **Referrals** tab shows the link (`/auth?mode=register&ref=CODE`). When an invited user's ad-wallet deposit is confirmed, **50% of what they paid** lands in the inviter's referral balance (exactly once — same transaction as the credit; subscription payments do not earn commissions). The same tab has the **withdraw** form: pick a coin, paste your address, and the payout is sent on-chain through BlockBee; your balance is deducted only after the transfer confirms (failed payouts never take the money). The e2e suite covers the whole chain against a mock processor: `bash scripts/run-blockbee-e2e.sh` (69 checks).

**Premium subscriptions.** `/premium` sells two plans with the same processor: **Premium $5/mo · $30/yr** (job alerts by email + personal Telegram bot) and **Premium+ $15/mo · $90/yr** (adds editorial publishing — 5 posts per calendar month in the curated sections — plus post statistics). Checkout is server-priced (the client never sends an amount): pick plan × period × coin → unique BlockBee address → the modal polls until the on-chain confirmation activates the plan (+30/+365 days, renewals stack). The paywall is absolute: users without an ACTIVE paid plan never receive job alerts — the dispatch worker filters them out, `/alerts on` in the Telegram bot answers "🔒 Job alerts are a Premium feature", and the header shows "Premium Active ✓" while a subscription runs. Underpaid orders (<90% of the price) do not activate — they are logged in the `PaymentLog` for manual resolution. Operator overrides: `bun run premium:grant <email> <days>` or `/grant`/`/revoke` in the admin bot (a grant without an expiry never expires). e2e: `bash scripts/run-premium-e2e.sh` (81 checks).

**Site CMS.** In the Telegram admin bot tap **👥 Manage team** (pick a member → send a text for the bio, or a photo for the avatar) or **🖼 Change logo** (send the photo — it becomes the **browser-tab icon/favicon**, served by `/api/favicon`; the visible site UI is wordmark-only by design). Uploads are stored in the database and take effect within a minute (60 s cache). Nothing else to configure.

### The 30-second minimal setup

For a first local Docker run you only need four values:

```bash
cp .env.example .env
# .env:
#   APP_URL=http://localhost:3000                       (already the default)
#   POSTGRES_PASSWORD=$(openssl rand -base64 24)        → paste output
#   AUTH_SECRET=$(openssl rand -base64 48)              → paste output
```

Everything else can be filled in later, one feature at a time — each optional
